# ArkoPy: как устроен текстовый арканоид

Документ о том, **как** сделана игра и **почему** именно так: модель мира, физика,
движение ракетки, ввод в терминале, отрисовка, масштабирование под размер окна и
тестирование. В конце — хронология найденных багов (она местами интереснее самого
кода) и справочник констант.

Для запуска и управления читай [README.md](README.md), здесь — внутренности.

```
arkanoid.py            ~1400 строк, зависимостей нет, только стандартная библиотека
tests/test_physics.py  43 теста, тоже без curses
```

---

## 1. Главный принцип: физика не знает про терминал

Весь мир — это обычный Python без `curses`: `World`, `Arena`, `Ball`, `PowerUp` и
одна функция

```python
advance(world, dt) -> list[str]     # продвинуть мир на dt секунд, вернуть события
```

`curses` живёт выше: `Game` (ввод, цикл, размеры окна) и `Renderer` (вывод).
Разделение не косметическое — оно даёт три вещи:

1. **Тесты без терминала.** `python3 -m unittest` гоняет физику в CI и на машине
   без TTY.
2. **`--smoke N`** — прогон мира на скорость в разы быстрее реального времени с
   проверкой инвариантов (раздел 9). Именно так были найдены почти все серьёзные
   баги: они не видны глазом, но видны по числам.
3. **Фиксированный шаг симуляции**, независимый от того, сколько реально рисовал
   терминал.

Поток одного кадра (`Game.run`):

```
getch() …(пока есть клавиши) → KeyDecoder → KeyRepeatTracker → команды ракетке
        ↓
now = monotonic(); frame_dt = min(now - prev, 0.25)
        ↓
аккумулятор: while acc >= 1/fps: events += advance(world, 1/fps)   # фиксированный шаг
        ↓
Sound.play(events) → сообщения (Уровень N / Мимо! / Бонус)
        ↓
Renderer.draw(world, …) → diff-буфер → addstr только изменившихся клеток
        ↓
napms(остаток кадра)
```

`frame_dt` ограничен 0.25 с: если терминал завис (например, в него печатают),
шарик не должен телепортироваться через половину поля. Внутри одного шага число
подшагов ограничено `MAX_STEPS_PER_FRAME = 4` по той же причине.

## 2. Модель мира

| объект | что хранит | зачем |
| --- | --- | --- |
| `Config` | fps, жизни, ширина ракетки, скорость, `level_seconds`, `max_arena_width`, путь к рекорду, зерно ГСЧ | все настройки в одном месте, приходят из `argparse` |
| `Arena` | `left/right/top/bottom` — координаты рамки | вся геометрия вычисляется из неё, поэтому ресайз = пересчитать арену |
| `World` | счёт, жизни, уровень, кирпичи, шарики, бонусы, состояние ракетки, эффекты, `rng` | единый источник правды; сериализуем, детерминирован при заданном зерне |
| `Ball` | `x, y, vx, vy, acc, stuck, dead` | `acc` — накопитель дробного движения (см. ниже) |
| `PowerUp` | `x, y (float), kind` | падает вниз, ловится ракеткой |

Ключевые производные величины — свойства, а не поля, чтобы не разъезжались при
ресайзе:

```python
World.size_scale           # во сколько раз арена больше эталонной (40×16)
World.speed                # клеток/с, зависит от размера поля и уровня
World.paddle_speed         # 3.4 × speed
World.paddle_accel         # 16 × paddle_speed
World.max_vx               # предел угла шарика = 3
World.paddle_min / paddle_max   # куда ракетке можно встать
World.brick_layout()       # ряды, колонки, отступ, плотность кладки
```

### Система координат

```
row 0        строка счёта (Счёт · Рекорд · ♥♥♥ · Уровень)
arena.top    верхняя стенка  ─
arena.top+1  «потолок» — самая верхняя строка, куда заходит шарик
arena.top+2  первый ряд кирпичей
…            поле
arena.bottom-1  строка ракетки
arena.bottom    нижняя стенка: долетел сюда — жизнь потеряна
arena.bottom+1  подсказка по управлению
```

Рамка занимает всё окно за вычетом этих служебных строк; `--arena-width N` может
ограничить ширину (уровни становятся короче — раздел 8).

### Инварианты, за которыми следит `--smoke`

* шарик всегда внутри `[left … field_right] × [ceiling … floor]`;
* у летящего шарика `1 ≤ |vx| ≤ max_vx` и `|vy| = 1` (нулевой `vx` — это «столб»,
  см. баг №1);
* ракетка не выезжает за `[paddle_min … paddle_max]`;
* кирпичи разрушаются, уровни кончаются (иначе игра «вечная» по ошибке, а не по
  правилам).

## 3. Физика шарика

### Дробное движение по целой сетке

Скорость измеряется в клетках в секунду, но мир — целочисленная сетка. Поэтому у
шарика есть накопитель:

```python
ball.acc += world.ball_speed_now * dt     # клетки, накопленные за кадр
while ball.acc >= 1.0:                    # сколько целых шагов «накопилось»
    ball.acc -= 1.0
    шаг()
```

На практике это означает: скорость меняешь **плавно** (`--speed`, ускорение по
уровням, замедляющий бонус), а мир по-прежнему живёт клетками, и коллизии остаются
точными. Если скорость выше 1 клетки/кадр, while делает несколько шагов за кадр —
и каждый проверяется отдельно, поэтому кирпичи не проскакиваются.

### Шаги раздельны по осям

```python
if move_x(...) and not ball.dead:   # шаг по X: мог упереться в кирпич/стену
    move_y(...)                     # шаг по Y: потолок, ракетка, кирпич, пол
```

Зачем именно так, а не «сдвинули (vx, vy) и посмотрели, куда попали»:

* **Одно столкновение — один отскок.** При диагональном шаге в угол стены и
  кирпича одновременно непонятно, какую ось отбивать; раздельный шаг отвечает на
  это сам.
* **Никакого туннелирования.** `move_x` идёт по одной клетке за проверку, даже
  если `|vx| = 3`.
* В прошлой версии отскок «по оси» определялся сравнением `old_y` и нового `y`,
  и ветка «боковое попадание» была мертва: `vy` никогда не был нулём.

### Кирпичи и прочность

Кирпич — это число: 0 (пусто), 1 `▒`, 2 `▓`, 3 `█`.

```python
damage_brick(world, x, y, events) -> None | False | True
#   None  — кирпича нет
#   False — треснул, но держится → шарик отскакивает
#   True  — разбит  → шарик летит ДАЛЬШЕ сквозь выбитую клетку
```

Пропускать разбитый кирпич («плуг») — самое сильное изменение в ощущении игры:
диагональный проход выбивает целую лесенку, а не один кирпич, и широкий уровень
становится проходимым. Обратная сторона — прочный кирпич (`▓`, `█`) наоборот
отбивает шарик и стоит нескольких подлётов, поэтому он появляется только там, где
на него есть бюджет времени (раздел 8).

### Отскок от ракетки: угол вместо рандома

```python
offset = ball.x - центр_ракетки
|offset| ≥ half            → самый крутой угол (|vx| = max_vx)
ближе к центру             → пологий (от 1 до max_vx)
offset == 0                → угол сохраняется как был
```

Два следствия, оба важны:

1. `|vx|` никогда не 0 — вертикального «столба» не существует в принципе;
2. игрок **рулит разбросом**: край ракетки отправляет шарик в дальний угол поля,
   центр оставляет там же, где он был. Это и есть управление в арканоиде.

### Бонусы

Из разбитого кирпича с шансом `POWERUP_CHANCE = 0.12` падает `E` / `S` / `L` / `M`
(шире ракетка, замедление, жизнь, ещё шарик). Эффекты — таймеры в
`world.effects`, поэтому `paddle_width` и `ball_speed_now` — свойства, а не поля:
истёк таймер — значение само стало прежним. Мультишарик даёт зеркальный шарик, но
не больше трёх на поле.

### Анти-залипание

`world.since_brick` растёт, пока шарик не тронет ни один кирпич. Если прошло
`STALL_SECONDS = 5` секунд — игра **наводит шарик на ближайший целый кирпич**:

```python
target = nearest_brick_column(world, ball.x)
если почти над ним          → vy = -1 (идём вверх)
иначе                       → меняем и знак, и наклон: |vx| 1 ↔ max_vx
```

Почему нельзя было просто «сменить направление на противоположное»: траектория
отражается зеркально и тот же цикл повторяется. Меняется **наклон** — и орбита
разрушается. Механика видна на числах: без неё последние кирпичи уровня
ждутся десятками секунд (было 26 «залипаний» на 26 кирпичей — то есть почти каждый
кирпич требовал спасения).

## 4. Движение ракетки

Ракетка — тележка с массой, а не курсор. Три величины:

```python
paddle_cmd   # куда просит игрок (вещественная «командная» позиция)
paddle_pos   # где ракетка на самом деле; догоняет cmd с ограниченным ускорением
paddle_vel   # текущая скорость, клеток/с
paddle_x  = round(paddle_pos)   # только для отрисовки и столкновений
```

### Профиль скорости — трапеция

```python
разрешено   = sqrt(2 · a · |до_цели|)      # скорость, при которой ещё успеем встать в цель
желаемо     = sign · min(Vmax, разрешено)  # далеко — полка на максимуме, вблизи — торможение
paddle_vel += clamp(желаемо − paddle_vel, −a·dt, +a·dt)
```

Получается «разгон → полка → торможение точно в цель» без единой ветки «а теперь
прыгаем». Замер на терминале 80×24 (`Vmax = 133 кл/с`, `a = 2122 кл/с²`, 60 fps):

```
клеток за кадр при удержании →:  0.59  1.18  1.77  2.21  2.21  2.21 …
                                 └──── разгон 4 кадра (62 мс) ────┘└ полка
```

### Четыре режима ввода

| действие | что происходит | результат (замер в живом pty) |
| --- | --- | --- |
| тап `→` | `paddle_cmd += 1` | ровно **1 клетка**, потом ноль скорости |
| 10 тапов | 10 раз по клетке | ровно **10 клеток**, накопления ошибки нет |
| держать `→` | команда уезжает каждый кадр на `Vmax·dt` | **24–32 клетки за 1 с**, в конце — упор в стенку |
| отпустить | команда больше не уезжает, `paddle_vel` гасится | плавный съезд **3.09 клетки** (теория `v²/2a` = 4.14) и остановка |
| `Home` / `End` | команда ставится у стенки | ракета едет сама, тормозя перед стенкой |
| мышь | команда под курсором | доезжает без перелёта |

### Почему «отпускание» — это торможение, а не «цель = точка остановки»

Первая версия была «правильной на бумаге»: при отпускании ставим целью точку
полной остановки. Не работает: точку надо пересчитывать каждый кадр, и получается
«бегущие ворота» — по тормозной кривой ракета *всегда* ещё успевает встать в цель,
то есть никогда не тормозит. Замерено: пронос **30 клеток вместо 4**. Поэтому
торможение вынесено в отдельный режим `glide_paddle_to_stop()` и просто гасит
скорость с тем же ускорением.

### Предсказание прибытия (и почему оно не телепортирует назад)

На 60 fps шаг быстрой ракетки больше клетки, поэтому цель проскакивается за кадр,
и контроллер начинает «звенеть» вокруг неё — это и есть видимые рывки. Лечение:
если новый кадр проскакивает цель, встаём ровно на ней. Условие сработает, только
когда скорость направлена **к цели**: иначе ракета, уже пролетевшая цель,
телепортировалась бы назад (это ломало честный съезд после отпускания).

## 5. Ввод: три ловушки терминала

### 5.1 ncurses не добирает хвост escape-последовательности

Опрос без блокировки (`nodelay(True)`) нужен, чтобы не стоять в `getch()`. Плата —
ncurses не ждёт остатка экранированной последовательности, и если терминал не
перешёл в application cursor mode (или в `terminfo` нет обычной формы `kcuf`),
вместо `KEY_RIGHT` приходят отдельные байты:

```
послано ESC [ C  →  getch(): 27, 91, 67      # «стрелки не работают»
послано ESC O C  →  getch(): 261 (KEY_RIGHT)
```

`xterm-256color` знает только application-форму (`kcuf1=\EOC`), так что на части
терминалов стрелки не работали бы вообще. Для этого в игре свой `KeyDecoder`:

```python
ESC [ C | ESC O C | ESC [ 1 ; 5 C → KEY_RIGHT      # + левая/вверх/вниз, Home, End
одинокий ESC                      → ничего (не выход!)
ESC [ <0;42;12M (мышиный мусор)   → ничего, а не буква «M»
```

Отдельно: **Esc не выходит из игры**. В некоторых конфигурациях это часть
последовательности стрелок, и выход получался бы случайным; выход — только `q`.

### 5.2 Автоповтор клавиши бывает очень разным

Клавиатурного события «отпустили» в терминале нет; удержание выглядит как тот же
код с постоянным интервалом — 30 Гц в эмуляторе, 6–10 Гц по SSH. Фиксированное
окно удержания 0.15 с давало на медленном автоповторе подёргивание в такт
нажатию, а на быстром — уезд на десятки клеток после одного тапа.

`KeyRepeatTracker` **выучивает интервал** конкретного терминала:

```
первое нажатие серии          → это тап: ровно +1 клетка
следующее в пределах пояса    → это автоповтор: «держат», дальше толкаем каждый кадр
интервал = EMA(0.5) от фактов, пояс 0.45…2.2× , границы 15…200 мс
повтор кончился (> 1.7 интервала) → клавишу отпустили → плавное торможение
```

`active_direction()` возвращает направление **только после подтверждения повтора** —
до второго события мы ещё не знаем, тап это или удержание (иначе тап уезжал на 7
клеток, пока не «дотормозил»). Смена направления всегда начинает новую серию.

### 5.3 Прочее

* `locale.setlocale(LC_ALL, "")` до `initscr()` — иначе при `LANG=C` curses рисует
  кириллицу пробелами (проверено в pty).
* `ESCDELAY=25` — быстрее отклик на одиночный Esc/Alt.
* `KEY_RESIZE` → `Arena.fit()` + `resize(world, …)`: пересчёт арену, арена-зависимых
  скоростей, кладки и ограничение ракетки.
* `Ctrl-L` → `Renderer.forget_screen()`: полная перерисовка, если терминал насорил.
* Работает и русская раскладка (`ф ы в` = `h l s`, `q` = `й`).
* Совместимость: `getmouse`, `mousemask`, `use_default_colors` могут **отсутствовать**
  в сборке curses — это `AttributeError`, а не `curses.error`. Все опциональные
  функции достаются один раз через `_curses_func()`, а ловится
  `CURSES_FAILURE = (curses.error, ValueError, AttributeError)`. Нет мыши — играем
  с клавиатуры, нет цвета — монохром.

## 6. Отрисовка

### Покадровый буфер и вывод отличий

Полная перерисовка каждого кадра (`erase()` + всё заново) на curses заметно
мерцает. Поэтому `Renderer` держит два побайтовых «экрана»:

```python
cells[y][x] = (символ, атрибут)     # что должно быть в этом кадре
prev[y][x]  = (символ, атрибут)     # что мы отправили в прошлый раз
flush(): сравнить строки, сжать соседние одинаковые клетки в прогоны,
         addstr() только изменившиеся прогоны, затем обмен буферами
```

Эффект двойной: нет мерцания, и в терминал уходит **≈22 байта на кадр** вместо
2–4 КБ полной перерисовки сцены 80×24 (замер в pty при 60 fps). `forget_screen()` обнуляет `prev` — следующий кадр redrawнется целиком
(`Ctrl-L`, ресайз).

### Символы и цвета

| смысл | UTF-8 | если терминал не UTF-8 |
| --- | --- | --- |
| кирпич 1/2/3 прочности | `▒ ▓ █` | `#` |
| шарик | `●` | `O` |
| ракетка | `▬` | `=` |
| стенки | `│ ─` | `| -` |
| жизни | `♥♥♥` | `ooo` |
| бонусы | `E S L M` | они же |

Цвет — `init_pair()` по числу прочностей (жёлтый/пурпурный/голубой) плюс зелёная
ракетка, белый шарик, синяя рамка. Всё обёрнуто в `CURSES_FAILURE`: не смог —
работаем атрибутами (`A_BOLD`, `A_DIM`, `A_REVERSE`), совсем плохо — монохром.

### Оверлеи

Пауза, «ИГРА ОКОНЧЕНА» и плавающие сообщения рисуются в тот же буфер
`A_REVERSE`-плашкой по центру. Сообщения (`Пробел — запустить шарик`, `Мимо!
Жизней: 2`, `Уровень 3`) живут `message_until` — таймером, а не отдельным экраном,
чтобы не плодить состояния.

## 7. Звук

Только `curses.beep()` / `curses.flash()` — внешней библиотеки в проекте нет.
Два ограничения, из-за которых звук был нестерпимым:

* `flash()` (белая вспышка всего экрана) уместен **только** при потере жизни и в
  конце игры; на каждый отскок — только `beep()`;
* на быстрых шариках событий бывает 5–10 за кадр: `Sound.play()` отправляет не
  более одного сигнала в 40 мс, иначе получается непрерывная сирена.

Клавиша `s` переключает на ходу; состояние видно в плавающем сообщении.

## 8. Очки, прогрессия и масштабирование под размер терминала

### Очки

* кирпич: `10 + 2·min(комбо, 10)`, комбо растёт за каждый разрушенный кирпич и
  обнуляется касанием ракетки — то есть награждает длинные серии;
* треснувший, но устоявший кирпич: `2`;
* рекорд пишется в `~/.local/share/arkanoid/score.json` (переменная
  `ARKANOID_SCORE` перебивает путь; пустое значение не должно превращать путь в
  `.`, а `~` обязан раскрываться, иначе в рабочей папке появляется каталог с
  именем `~`).

### Уровни

Карты — строки в `LEVELS` (`#` `%` `&` = прочность 1/2/3, `.` = пусто), тайлятся по
ширине, поэтому одна и та же карта годится и окну в 40 колонок, и в 200. С уровнем
растёт число рядов (`1 + level//2`) и плотность кладки, а прочность кирпича
ограничивается бюджетом времени.

### Формула времени уровня

Выведена из модели и подтверждена симуляцией:

```
время уровня ≈ ширина_поля × прочность_кирпича × (2 × высота_поля / скорость)
```

Почему **ряды и густота кладки в формулу не входят**: за один подлёт шарик проходит
по одной клетке в каждом ряду, поэтому «число кирпичей» и «шанс в них попасть»
всегда одного порядка и сокращаются. Сквозь разбитый кирпич он летит дальше
(раздел 3), так что лесенка из `▒` выбивается за тот же подлёт, что и одиночный
кирпич. Следствия:

* толщина стены — это **сложность и внешний вид**, а не темп игры;
* темп задают скорость шарика и ширина поля;
* на очень широком терминале уровень длиннее — это физика жанра, а не настройка:
  чтобы выбить последний кирпич, шарик обязан побывать в этой колонке.

Отсюда же ограничители:

| константа | зачем |
| --- | --- |
| `MAX_VX = 3` | при `|vx| = 4` ракетка не успевает за шариком: в симуляции — 285 потерянных жизней за 200 с вместо 3 |
| `PADDLE_TO_BALL = 3.4` | ≈ `1.15 × MAX_VX`: меньше — не догоняет на диагонали (при 2.0 было 131 смертей), больше — проезжает за кадр слишком много клеток |
| `MIN_REACTION_SECONDS = 0.35` | за сколько секунд шарик пролетает высоту поля; ниже — человек не успевает среагировать, и разгонять «чтобы уровень был короче» нельзя |
| `PADDLE_ACCEL = 16/с` | компромисс между «плавно» и «не проскакивает цель»: разгон 62 мс, съезд ~3 клетки |

### Замеры (болван-игрок, 200 с непрерывной игры)

| терминал | поле | `Vmax` шарика | стена 1-го уровня | прогноз пробоя | итог за 200 с |
| --- | --- | --- | --- | --- | --- |
| 40×14 | 38×10 | 21 | 38×3 | ~45 с | 3 уровня, 4 смерти |

python3 -m unittest discover -s tests -v

### `--smoke` — баланс и инварианты без терминала

```bash
python3 arkanoid.py --smoke 200 --seed 3 --size 200x60
# прогон 200 с на 200x60 (арена 198x56, стена 198x2, скорость 160, пробой ~139 с):
#   очков 4744, разбито 315, уровней пройдено 1, жизней потеряно 4
```

Крутит `advance()` на скорости много выше реальной, после каждого кадра сверяет
инварианты и в конце печатает сводку; ненулевой код возврата — если что-то нарушено.
Удобная часть: `--seed` делает прогон повторимым, `--size` — проверяет любой
терминал, не меняя окно.

### Болван игрока

`aim_ai_paddle()` ставит ракетку **в точку прибытия** шарика (мини-симуляция с
отражениями от стенок), а не туда, где шарик сейчас — так играет человек. Это не
мелочь: реактивный болван, следующий за координатой шарика с опозданием на кадр,
на больших полях давал **285 смертей за 200 с** и ломал все замеры баланса,
притворяясь игроком-неумехой. С предсказывающим — 3–4 смерти, как у живого
игрока.

## 10. Хронология багов (симптом → причина → что сделано)

Полезный раздел, потому что почти ничего из этого нельзя было увидеть глазами.

1. **«Стоб» вместо игры.** Удар в центр ракетки давал `vx = 0` → шарик гонял
   вверх-вниз по одной колонке, принося очки вечно: **47 649 очков за 2 млн шагов**
   без единой потери жизни. Причина: нулевой `vx` разрешён. Теперь `1 ≤ |vx| ≤ 3`,
   а угол зависит от точки удара. Инвариант следит `--smoke`.
2. **Уровень нельзя пройти никогда.** Отскок от стенки считался как
   `nx <= left`, из-за чего крайние колонки поля были недостижимы — а в них висели
   кирпичи. Софт-лок на ровном месте: всегда оставалось 4–8 кирпичей. Проверка
   перенесена на «следующая клетка **за** полем», регрессия —
   `test_ball_reaches_extreme_columns_and_bounces`.
3. **Отскок «по совпадению строки».** `ball_y == paddle_y` работал, только пока
   шарик проходит ровно одну клетку за шаг. Проверка пересечения линии
   (`old_y < paddle_y <= ny`) держит и быстрый шарик, и `--fps 30`.
4. **Мёртвая ветка «боковое попадание».** Ось отскока определялась сравнением
   старых и новых `y`, но `vy` никогда не был нулём → боковые столкновения не
   обрабатывались, угол кирпича проскакивался по диагонали. Раздельные оси.
5. **Ресайз ломал игру.** Размер читался один раз на старте: после изменения окна
   ракетка уезжала за экран, шарик рисовался в несуществующих координатах,
   кладка оставалась старого размера. Теперь `KEY_RESIZE` → `Arena.fit()`.
6. **Кириллица пропусками при `LANG=C`.** Без `setlocale` curses молча рисовал
   пробелы (проверено в pty: 7 пробелов вместо «Счёт»). Плюс ASCII-фолбэк глифов,
   если терминал правда не UTF-8.
7. **Звук-сирена.** `flash()` на каждое событие и beep на каждый отскок. Вспышка
   осталась только для потери жизни, beep ограничен 40 мс.
8. **Стрелки не работали** на терминалах без application cursor mode
   (`27, 91, 67` вместо `KEY_RIGHT`) → свой `KeyDecoder`.
9. **Удержание/тап не различались** (фиксированное окно 0.15 с) → тап уезжал на
   десятки клеток, а на медленном автоповторе появлялось подёргивание → `KeyRepeatTracker`.
10. **«Бегущие ворота» при торможении**: цель = точка остановки, пересчитываемая
    каждый кадр, → ракета проезжала 30 клеток вместо 4 → отдельный режим
    торможения.
11. **Звенение вокруг цели**: шаг ракетки больше клетки → проскок → обратно →
    предсказание прибытия (с проверкой направления, иначе телепорт назад).
12. **`AttributeError: curses.getmouse`** на сборках без мыши: `except
    curses.error` его не ловит → `CURSES_FAILURE` и `_curses_func()`.
13. **Папка `~` в рабочей директории**: `Path("~/.local/…")` без `expanduser()`
    создавал каталог с именем `~`; пустая `ARKANOID_SCORE=""` превращала путь в `.`.
14. **Ложные выводы из тестов.** Реактивный болван («285 смертей», «уровень
    непроходим») и собственный мини-эмулятор VT100 в pty (следы шарика, «хвост»
    старого сообщения) оба врали: ncurses стирает символ через `\x08 ` и использует
    `ESC [ nP`, которых эмулятор не знал. Прежде чем чинить игру, стоило проверить,
    что сломано не измерение: финальную картину подтверждали юнит-тестом рендерера
    (старые клетки реально затираются пробелами).

## 11. Известные ограничения

* **Сетка — это разрешение.** Плавность ограничена размером клетки и частотой
  кадров: при 120 fps шаг в клетках на кадр вдвое меньше, но полуклеток не бывает.
  Позиция ракетки хранится вещественно, рисуется округлённо.
* **Отпускания клавиши нет.** `KeyRepeatTracker` оценивает интервал автоповтора;
  на экзотических режимах повторения (например, 1.7 Гц) окно может не выучиться —
  тогда движение остаётся таповым, но не ломается.
* Широкий терминал ⇒ длинные уровни (формула в разделе 8). Спасает
  `--arena-width`.
* Мышь работает там, где её пробрасывает терминал (`tmux` по умолчанию — нет).
* `--smoke` балансирует по болвану-игроку: живой игрок слабее в реакции, но сильнее
  в разбросе, так что цифры — ориентир, а не обещание.
* Рекорд пишется синхронно (в конце партии) и без блокировок: две запущенные
  копии могут перезаписать счёт друг друга.
* Нет лицензии и CI — репозиторий учебный.

## 12. Что можно делать дальше

1. `pyproject.toml` + ruff + GitHub Actions на `unittest` и `--smoke` (тесты уже
   не требуют TTY, CI получится тривиальным).
2. Kitty keyboard protocol: настоящие события нажатия/отпускания — и
   `KeyRepeatTracker` станет не нужен.
3. Рендер полублоками (`▄▀`) — фактически удвоенное вертикальное разрешение,
   гладкость движения без роста fps.
4. «Прилипшая» ракетка (`C`-бонус), лазеры, движущиеся кирпичи — физика к этому
   готова: все столкновения уже разнесены по осям и возвращают события.
5. Таблица рекордов (топ-N вместо одного числа), экспорт серии в GIF через
   `pyte`-подобный захват кадров.

## 14. В каком порядке читать код

1. `Arena` и `World.__post_init__` — как из размеров окна получается игра.
2. `advance()` — 30 строк, из которых видно все правила.
3. `move_x` / `move_y` / `damage_brick` — столкновения.
4. `move_paddle` → `follow_paddle_command` → `glide_paddle_to_stop` — ракетка.
5. `KeyDecoder` и `KeyRepeatTracker` — почему ввод в терминале это отдельная задача.
6. `Renderer` — вывод отличий вместо перерисовки.
7. `Game.run` — цикл с фиксированным шагом; и `run_smoke` — тот же мир без экрана.
