# spr.py — как устроено (справочник для доработок)

`spr.py` — интерактивная модель движения ракетки арканоид: ракета на экране,
клавиатура, четыре параметра движения из командной строки. Это НЕ игра и НЕ
полигон алгоритма `arkanoid.py`:

| файл | для чего |
| --- | --- |
| `arkanoid.py` | игра: физика шарика, кирпичи, отрисовка, ввод |
| `speed.py` | безголовый полигон **того же алгоритма игры** (сервопривод `cmd`/`pos`/`vel`, сценарии, метрики game feel, `--tune`) |
| `spr.py` | **подбор четырёх параметров пальцем**: параметрическая модель v(t) на экране, результат виден глазами, плюс `--trace`/`--check` без терминала |

Алгоритм в `spr.py` сознательно проще игрового: здесь нет «командной позиции»
`cmd` и сервопривода, а есть фазовый автомат с явными формулами — ровно теми,
которые задаются параметрами. Поэтому числа из `spr.py` переносятся в игру как
*соотношение* V / a / Vmax / a_t, а не как константы (см. §11).

Единицы везде общие с игрой: **клетка** = колонка терминала, **секунды**,
**клеток/с**, **клеток/с²**.

---

## 1. Запуск, параметры, коды выхода

```bash
python3 spr.py                            # 0.05 с · 30 · 120 · 90
python3 spr.py 0.12 20 40 60              # те же четыре числа позиционно
python3 spr.py --pause 0 --speed 40       # мгновенный отклик
python3 spr.py --pause 0 --exact-tap      # тап = ровно клетка (ценой окна)
python3 spr.py --trace 0.8 --fps 30       # лента кадров без терминала
python3 spr.py --check                    # 16 инвариантов, !=0 = сломано
```

Четыре параметра принимаются **и позиционно (в этом порядке), и флагами**;
флаг перекрывает позиционный (`motion_from_args` → `first(...)`).

| # | параметр | флаг / позиция | единицы | по умолчанию | где живёт |
| --- | --- | --- | --- | --- | --- |
| 1 | пауза перед началом движения | `--pause` / 1 | с | 0.05 | `Motion.pause` |
| 2 | скорость движения | `--speed` / 2 | клеток/с | 30 | `Motion.speed` |
| 3 | ускорение при удержании | `--accel` / 3 | клеток/с² | 120 | `Motion.accel` |
| 4 | максимальная скорость | `--max-speed` / 4 | клеток/с | 90 | `Motion.max_speed` |

Служебные флаги: `--brake` (торможение a_t, клеток/с²; по умолчанию
`max(30, 21·V)`), `--tap-step` (клеток за тап), `--exact-tap`, `--ready`
(блокировка ввода на старте), `--fps` (клампится в 5…240), `--width` (ракета в
клетках), `--size` (поле для `--trace`/`--check`), `--repeat-hz` (частота
автоповтора в головых режимах), `--no-color`.

`Motion.capped()` приводит набор к согласованному: `pause ≥ 0`, `speed ≥ 0.5`,
`accel ≥ 0`, `max_speed ≥ speed`, `brake ≥ 1`, и возвращает строку
предупреждения, если что-то поправил (`main` печатает её в stderr).

Коды выхода: `0` — выход по `q` / `--check` зелёный; `1` — терминал не годится
или правило нарушено; `2` — нет интерактивного терминала (для модели есть
`--trace`/`--check`).

## 2. Слои файла

Порядок сверху вниз = порядок зависимостей (верхний слой ничего не знает о
нижних, кроме как через аргументы):

| слой | что | раздел файла |
| --- | --- | --- |
| константы | параметры по умолчанию, окно автоповтора, имена фаз | «Автоповтор терминала», «Параметры движения» |
| `Motion` | четыре параметра + производные (`dec`, `shelf_time`, `confirm_window`, `capped`) | frozen dataclass |
| `Paddle` | состояние ракетки + **один шаг физики** `step(dt)` | никаких curses |
| `KeyRepeatTracker` | тап против удержания по интервалу автоповтора + задержка его старта | никаких curses |
| `KeyDecoder` | добор escape-последовательностей | никаких curses |
| `View` | геометрия показа (поле, границы, ширина ракеты, строки) | curses не трогает |
| `Canvas` | построчный буфер + diff-вывод, глифы, цвета | curses |
| `Readout`, `readout`, `sparkline`, `speed_bar`, `draw` | что и как показывать | curses |
| `App`, `run_app` | живой цикл: ввод → `Paddle.step` → `draw` | curses |
| `Frame`, `Rig`, `trace`, `print_summary` | головая прокрутка тех же кодов | без curses |
| `Rule`, `rule_*`, `RULES`, `check` | 16 инвариантов модели | без curses |
| `parse_args`, `motion_from_args`, `main` | CLI и развилка режимов | — |

Три входа в одну и ту же физику: `App.run` (живой), `Rig.run`
(`--trace`/`--check`), `Paddle.step` напрямую (`rule_pause_in_flight`).
**Правило: что бы ни менялось в движении — менять только `Paddle`, а не
повторять логику в `App`/`Rig`.** И наоборот, `Rig.run` обязан зеркалить
последовательность вызовов `App.run` (keys → `set_holding` → `confirm_gap` →
`step`), иначе `--check` проверяет не то, что происходит в терминале.

## 3. Модель движения

### 3.1 Состояние `Paddle`

| поле | смысл |
| --- | --- |
| `pos` | где ракета (вещественная клетка); рисуется в `x = floor(pos + 0.5)` |
| `vel` | клеток/с, со знаком направления |
| `vel_frame` | скорость на начало кадра — нужна для интегрирования «по средней» |
| `key` | направление последней серии нажатий (−1/0/+1) |
| `holding` | автоповтор жив = клавишу держат (пишет `set_holding` из цикла) |
| `wait` | остаток паузы `--pause` |
| `pending` | **окно подтверждения удержания**: тяга уже открыта, но тап это или удержание — терминал ещё не сказал |
| `tap_target` | клетка тапа «на всякий случай» (`_anchor`) |
| `target` | адрес (тап / Home / End / Space) |
| `phase` | `покой · пауза · разгон · тап · адрес · торможение` (+ отображаемая `газ?`) |
| `boost` | адрес с разгоном до Vmax (Home/End) или ограниченный базой V (тап) |
| `run_t` | сколько секунд тяга открыта (для метрик) |
| `press_at`, `move_at`, `shelf_at`, `shelf_lag`, `peak` | метрики серии для показа «задано / замерено» |
| `confirm_gap` | выученный интервал автоповтора; цикл пишет сюда `tracker.gap` каждый кадр |
| `min_x`, `max_x`, `width` | границы левого края ракеты и её ширина (для показа) |

### 3.2 Фазы и переходы (`step`, единственный владелец перехода)

```
                    ┌────────────── повтор пришёл (holding) ──────────────┐
                    │                                                      ▼
 press(новая серия)─┤ pause>0:  ПАУЗА ──(wait истёк)──> _start() ──> РАЗГОН(газ)
                    │ pause=0:  ────────────────────────────────────> РАЗГОН(pending)
                    │                                                            │
 РАЗГОН ──(pending истёк, повторов не было)──> _settle_tap() ──> ТАП или ТОРМОЖЕНИЕ
 РАЗГОН ──(holding=0, pending=0)──> ТОРМОЖЕНИЕ ──(v=0)──> ПОКОЙ
 ТАП/АДРЕС ──(повтор пришёл)──> РАЗГОН          ТАП/АДРЕС ──(цель пройдена)──> ПОКОЙ
 ПОКОЙ/ТОРМОЖЕНИЕ/ТАП ──(holding=1)──> РАЗГОН   (страховка от «газ потеряли раньше,
                                                чем трекер понял, что повторы кончились»)
```

Хвост каждого `step`: `_wall()` (стенка) → метрики (`move_at`, `peak`,
`shelf_at/shelf_lag`) → `trail.append(x)`.

### 3.3 Формулы (что именно обещают параметры)

* **Отклик.** С места ход начинается сразу с `V` (скачок 0 → V — аркадная
  модель; это единственное место, где скорость меняется разрывно, и
  `rule_reversal` её разрешает). При `accel = 0` это вырождается в «всё время V».
* **Разгон при удержании.** `|v| ← min(Vmax, |v| + a·dt)`, но не ниже `V`
  ⇒ в непрерывном времени `v(t) = min(Vmax, V + a·t)` и **время до полки ровно
  `(Vmax − V)/a`** — это проверяет `rule_shelf`.
* **Торможение (газ убрали).** `|v| ← |v| − a_t·dt`, путь `v²/(2·a_t)`.
  `a_t = dec` = `--brake` или `max(BRAKE_RATE_FLOOR=30, BRAKE_RATE=21 · V)`.
* **Встречная команда.** Гасится злее: `Motion.brake_like` = `a_t ·
  REVERSE_RATE(1.5)`, и только **до нуля** — через ноль скорость не прыгает,
  разгон в новую сторону начинается со следующего кадра (`_run`).
* **Тап и вообще любой адрес.** Кривая прибытия `|v| = min(лимит, √(2·a_t·d))`,
  где `d` — остаток до цели; лимит = `min(V, Vmax)` для тапа и `Vmax` для
  Home/End (`boost`). Если текущая скорость выше кривой, снижение идёт со
  скоростью тормоза, а не прыжком. Пересечение цели ловится проверкой
  `(target − pos)·distance ≤ 0` и даёт точную остановку на цели.
* **Следствие из кривой прибытия:** до цели всегда хватает торможения, поэтому
  адрес не проскакивается, а «ровно клетка» держится без накопления ошибки.

### 3.4 Интегрирование и деление кадра

* `step()` сначала двигает время модели (`time += dt`), потом меняет состояние,
  поэтому `press_at` — момент приёма команды, а `move_at`/`shelf_at` — **конец**
  кадра. Отсюда «замеренная задержка = пауза + ~1 кадр» в HUD и в правилах
  (допуск `+2.5/fps`).
* `_integrate()` считает путь **по средней скорости кадра**
  (`pos += (vel_prev + vel)/2 · dt`, как `glide_paddle_to_stop` в игре).
  Явная схема «новая скорость на весь кадр» на грубой сетке обнуляла торможение
  (гашение 30 → 0 за кадр давало нулевой путь, и тап недоедал половину клетки).
* Кадр, в котором пауза истекает посередине, **режется**: `_coast(passed)` +
  `_start()` + `_thrust(dt − passed)`. Раньше обе половины считали весь кадр, и
  ракета скакала на два шага (правило `rule_no_teleport` на это и ловило).
* `Frame.t` в головом прогоне — **конец** кадра (иначе на 30 fps казалось, что
  ракета сдвинулась во время паузы).

### 3.5 Тап против удержания: `pending`, `_settle_tap`, `--exact-tap`

Терминал не присылает «клавишу отпустили». Различить тап и удержание можно
только по **факту прихода/неприхода автоповтора**, то есть через
`confirm_window = HOLD_TOLERANCE (1.7) × выученный интервал` ≈ 57 мс при 30 Гц.

Модель выбирает «заплатить за точность задержкой» или «заплатить за скорость
неточностью тапа»:

| режим | задержка старта | одиночное нажатие |
| --- | --- | --- |
| `--pause P > 0` (по умолчанию) | ровно `P` | клетка + то, что проехала за окно подтверждения (≈ `V·1.7/gap + v²/2a_t`), тормозит в клетку тапа, если ещё успевает |
| `--pause 0` | 0 (тот же кадр) | то же, без паузы сверху |
| `--exact-tap` | `max(P, окно)` | **ровно `tap_step`**, целая клетка |

Механика: при старте серии тяга открывается сразу (`pending = окно`,
`tap_target = _anchor(dir)`), дальше

* пришёл повтор → `pending = 0`, газ чистый (`разгон`);
* окно истекло молча → `_settle_tap()`: если клетка тапа ещё впереди — `тап`
  (кривая прибытия в неё), если уже проедена — `торможение` (честная остановка,
  назад ракета не разворачивается).

Отсюда фаза `газ?` на экране: тяга есть, режим ещё не подтверждён.
Прошлая логика («повторов нет ⇒ это тап ⇒ тормозим в клетку») при `--pause 0`
успевала проехать клетку и **встать**: разгон стартовал только с первым
автоповтором (замер: ноль скорости к моменту подтверждения и разгон на 63 мс
после нажатия) — это и было «задержкой после нажатия», регрессия `rule_no_dip`.

### 3.6 Границы, стенка, адреса

* `min_x/max_x` — куда может встать **левый край** (`View.bounds`);
  `_wall()` прижимает к границе, обнуляет скорость и считает адрес у стенки
  выполненным (газа это не отменяет).
* `Home`/`End`/`Space` идут через `go_to()` → фаза `адрес` (`boost=True`,
  потолок Vmax, цель — стенка/центр).
* `fit`-аналог игры здесь — `handle_resize`: границы пересчитаны, ракета
  возвращена внутрь, скорость обнулена.

### 3.7 Метрики серии

`press_at` (команда принята) → `move_at` (первый кадр с `|v| > SNAP_SPEED`) →
`shelf_at`/`shelf_lag` (первый кадр с `|v| ≥ Vmax`, `shelf_lag` запоминается и
не теряется, когда скорость потом упала), `peak` (|v|max серии), `trail`
(deque последних 64 клеток — след на экране). Всё это показывается в HUD как
«задано / замерено»; `--trace` печатает те же величины по кадрам.

## 4. Ввод

### 4.1 `KeyRepeatTracker`

* `press(direction, now) -> bool` — `True`, если это повтор (держат).
* Новая серия: другой конец или первый код.
* Повтором считается **всё, что не медленнее** `min(REPEAT_GAP_LIMIT[1]=200 мс,
  gap · REPEAT_SLOW_EDGE=2.2)`. **Нижней границы больше нет**: «слишком частый»
  интервал — это тоже газ, потому что сетка кадров рвёт поток (60 fps + 30 Гц =
  интервалы 16.7/33/50 мс).
* `gap` = **медиана** последних `REPEAT_HISTORY=5` интервалов, попавших в
  правдоподобный коридор 15…200 мс. Медиана (а не EMA) — чтобы серия частых
  тапов не задирала окно; в обе стороны окно перестраивается само.
* `still_holding(now)`: повтор жив, пока с последнего кода прошло ≤
  `gap · HOLD_TOLERANCE (1.7)`; `active_direction(now)` — куда толкать ракетку
  в этом кадре (0, если не держат).
* Пакеты кодов (несколько кодов с одним `now`, когда fps ниже частоты
  автоповтора) попадают в «быстрее окна» ⇒ тот же газ, в выборку `gap` не
  лезут (интервал < 15 мс отбрасывается).

Почему так: прежняя версия требовала и нижнюю границу (`interval ≥ 0.45·gap`) и
училась только внутри окна. Серия тапов по ~80 мс задирала `gap` до ~70 мс,
настоящие повторы по 33 мс переставали попадать в окно и объявлялись новыми
тапами, удержание разваливалось на подскоки без разгона, и состояние было
**нелечимым**. Регрессия — `rule_hold_after_taps`.

### 4.2 `KeyDecoder`

При `nodelay(True)` ncurses не дожидается хвоста escape-последовательности, и
если в terminfo нет `kcuf=\e[C`, вместо `KEY_RIGHT` приходят байты `27 91 67`.
`KeyDecoder.feed` собирает `\e[C`, `\e[D`, `\eOA`, `\e[1;5C` и т. п.; `None`
означает «байт съеден, ждём продолжение». В конце каждого кадра декодер
сбрасывается, чтобы одинокий ESC не склеился со следующим нажатием.

### 4.3 Клавиши

| клавиша | действие |
| --- | --- |
| `← →`, `h l`, `р д`, `ф в` | тап = `tap_step`, держать = разгон |
| `Home` `End` `Space` | адрес: левая стенка, правая, центр |
| `+ −` | V ±5; `[ ]` — a ×1.5; `, .` — Vmax ±15; `o 0` — пауза ±0.02 с (наживо, через `set_motion` → `Motion.capped`) |
| `r` | сброс в центр, метрики и след с нуля, `--ready` ещё раз |
| `p` | заморозить показ (кадры не считаются, клавиши читаются) |
| `Ctrl-L` (и `Ctrl-R`) | `erase` + `Canvas.forget()` — полная перерисовка |
| `q` | выход (Esc — намеренно не выход: это начало последовательности) |

Во время `--ready` клавиши движения не кормят ни трекер, ни ракетку (`nudge` с
`locked=True`), иначе трекер выучил бы несуществующую серию.

## 5. Показ

* `View` — геометрия: `inner = width − 2`, стенки `wall_left/wall_right`,
  рабочее поле `left..right`, ширина ракеты `paddle_cells`
  (`clamp(round(inner/12), 6, 20)` или `--width`, но не шире поля),
  `bounds()` — границы левого края, `centered()`. Строки: 0 шапка, 1 рамка,
  2 линейка колонок, 3 след, 4 ракета, 5 дорожка (центр + точка остановки),
  6 рамка, 7..10 HUD, 12/13 подсказки, 14 формула. Отсюда `MIN_WIDTH=44`,
  `MIN_HEIGHT=15`.
* `Canvas` — два кадровых буфера и diff-`flush` (строки пробегаются runs'ами, `addstr` только
  туда, что изменилось; правый нижний угол проглатывается `CURSES_FAILURE`).
  `begin()` чистит кадр, `forget()` забывает предыдущий (после `Ctrl-L`).
* Глифы: UTF-8 против ASCII выбирает `_utf8_term()`, которая смотрит на
  `locale.nl_langinfo(CODESET)` **после** `setlocale(LC_ALL, "")` —
  `getpreferredencoding()` врёт из-за PEP 538 (C-локаль докоэрсит в C.UTF-8), и
  curses в жёстком `LC_ALL=C` молча съедает и псевдографику, и кириллицу. При
  не-UTF-8 `main` печатает предупреждение и рисует ASCII-набором.
* Цвета: 7 пар (`wall, paddle, target, dim, hud, warn, title`), ракета — цвет +
  bold + reverse; `--no-color` оставляет атрибуты без пар.
* `Readout`/`readout` превращают состояние в строки HUD: фаза (или `газ?`),
  v и % полки, клетка, шаг за кадр, «встанет в … (путь …)», полоса скорости,
  лента |v| за последние кадры, «задано» (pause/V/a/Vmax/тормоз/пик серии) и
  «замерено» (задержка старта против `expect_lag`, разгон до Vmax, частота
  автоповтора, длительность кадра).

## 6. Живой цикл `App`

```
handle_input()  → все getch за кадр, decode, handle_key (press/go_to/tune/quit)
now             → ready_left, held = tracker.active_direction(now)
                → paddle.set_holding(held == paddle.key)
                → paddle.confirm_gap = tracker.gap        ← окно подтверждения
accumulator     → пока ≥ step (не больше MAX_CATCHUP = 4 кадров догона): paddle.step(step)
draw(...)       → readout + полосу + HUD
napms(step − spent)
```

* Шаг физики **фиксированный** (`1/--fps`), реальное время только наполняет
  аккумулятор; просадка планировщика не телепортирует ракетку (`min(frame, 0.25)`
  и `MAX_CATCHUP`).
* Во время `--ready` и `p` (заморозка) физика не считается, но кадр рисуется и
  клавиши читаются — можно крутить параметры на стоячей картинке.
* `set_motion(**changes)` — живой тюнинг: пересобирает `Motion`, прогоняет через
  `capped()`, отдаёт новую ракетку в `Paddle` и `View`, текст предупреждения —
  в строку сообщения.
* `handle_resize` пересоздаёт буферы `Canvas`, пересчитывает `View`/границы,
  возвращает ракетку в поле и ругается, если стало тесно (`MIN_WIDTH` ×
  `MIN_HEIGHT`).

## 7. Головые режимы (без терминала)

### 7.1 `Rig` — та же цепочка ввода, только по расписанию

`Rig(motion, fps, bounds, width, repeat_hz)` + `run(keys, seconds, extra, start)`
где `keys = [(t, direction)]`, `extra = [(t, 'home'|'end'|'center', 0)]`.
Генераторы нажатий: `Rig.hold_events(t0, секунд, dir, hz)` (первый код + автоповтор
с частотой терминала) и `Rig.tap_events(t0, dir)` (один код). Порядок вызовов в
цикле совпадает с `App.run`, поэтому `--check` меряет именно живой путь.
На выходе — `[Frame(t, phase, vel, pos, held)]`, где `t` = конец кадра.

`start_of_motion(frames, t0)` — первый кадр, где **позиция** сдвинулась (не
скорость: на грубой сетке кадров тап успевает проехать клетку и погаситься
внутри одного кадра).

### 7.2 `--trace СЕК`

Симулирует удержание вправо на `СЕК` секунд, потом отпускание; печатает ленту
`t · фаза · v · x · шаг · сколько прошло после нажатия` (прорежая до ~220 строк)
и сводку: когда тронулась, пик, расчётное время до полки, пройдено, финал.
Строка фазы `газ?` в ленте не появляется (там печатается `phase`, а не метка),
но виден `held`.

### 7.3 Конверт применимости

`ENVELOPE_FPS = 15…120` и `ENVELOPE_REPEAT = 6…60 Гц`. Вне его `check()` печатает
`[!]`, а правила, зависящие от подтверждения удержания, **пропускаются**
(возвращают `True`), а не подгоняются порогами: на 4 Гц автоповтора удержание
вообще неотличимо от тапов, на 5 fps один кадр проносит дальше, чем ракетка
успевает затормозить.

## 8. `--check`: 16 инвариантов

Сценарии дают `rule_*(motion, fps, repeat_hz, bounds, width) -> True | str`
(строка = объяснение нарушения); падающее правило считается нарушением.
Хелперы: `_hold(...)` (удержание + хвост на полную остановку, возвращает
`frames, момент_отпускания`) и `_tap(...)` (возвращает `frames, rig` — rig нужен
для выученного интервала).

| ключ | правило | порог / смысл |
| --- | --- | --- |
| `pause` | во время паузы ракета стоит | до `t_press + pause` позиция не меняется вообще |
| `lag` | пауза выдержана ровно | `lag ∈ [want, want + 2.5/fps]`, `want = pause` (с `--exact-tap` — `max(pause, окно)`) |
| `tap` | тап = ровно `tap_step`, при целом шаге — на клетку | строгая клетка только в `--exact-tap`; иначе `shift ∈ [tap_step − 2 кадра пути, tap_step + ½(V+v_end)·окно + v_end²/2a_t + 2 кадра]`, старт ≤ `pause + 2.5/fps` |
| `vmax` | `\|v\| ≤ Vmax` | все кадры |
| `shelf` | разгон до Vmax = `(Vmax−V)/a` | отсчёт от первого кадра `разгон`, допуск 3 кадра |
| `release` | встала на тормозном пути | отсчёт от последнего кадра газа; `roll ≤ v²/2a_t + v/fps` |
| `step` | шаг за кадр ≤ `Vmax/fps` | ловит двойной счёт кадра и «телепорт» |
| `reverse` | внутри фазы `\|Δv\| ≤ max(a, 1.5·a_t)/fps` | скачки разрешены только на смене режима (отклик 0→V) и у стенки |
| `field` | ракета в поле при случайных нажатиях | фиксированное зерно ГСЧ, 12 с хаоса + Home/End/центр, финал — покой |
| `accel0` | `a = 0` → ход строго с V | медиана \|v\| по кадрам `разгон` равна V |
| `pause0` | `--pause 0` → движение в первом кадре | тронулась и открыла газ ≤ 2.5 кадра после нажатия |
| `repeat` | частые тапы не ломают следующее удержание | после 3 тапов удержание достигает Vmax без срывов в `пауза`, выученный интервал ≤ 3× настоящего |
| `slowterm` | медленный автоповтор (8 Гц) узнаётся | пик = Vmax, `gap ∈ [50, 250] мс` |
| `flight` | пауза в полёте: попутный ход бережёт, встречный гасит | вызов `Paddle` напрямую; внутри `паузы` \|v\| не падает попутно и падает навстречу |
| `nodip` | между нажатием и подтверждением нет провала v | от первого сдвиг до подтверждения \|v\| монотонно не убывает (дребезг автоповтора, давший `торможение`, не считается) |
| `exacttap` | `--exact-tap` даёт ровно клетку и при `--pause 0` | сдвиг = `tap_step`, старт = окно подтверждения ± 2.5 кадра |

Регрессионная ценность проверена: на возвращённых «старых» реализациях правила
дают `МИМО` (`repeat` → «пик 58.0 вместо полки 90», `nodip` → «провал 30.0 →
25.1», `flight` → «попутная пауза погасила ход с 44.0 до 23.0»).

Матрица, на которой всё зелёное (38 наборов): `--pause 0…5`, `a = 0`, V 5…200,
`--fps 15…240`, `--repeat-hz 4…60`, `--tap-step 0.5…3`, `--brake 30…10000`,
`--exact-tap` во всех комбинациях.

## 9. Хронология найденного (читать перед правками)

1. **«После тройного быстрого нажатия удержание не разгоняется».** Нижний край
   окна автоповтора + обучение только внутри окна ⇒ невылечимое завышение `gap`.
   Лечится: верхняя граница окна + медиана (§4.1). Регрессия `repeat`.
2. **«Задержка после нажатия» при `--pause 0`.** Модель до подтверждения решала
   «это тап», успевала проехать клетку и встать; разгон стартовал с первым
   автоповтором (замер: v = 0 к моменту подтверждения, газ через 63 мс).
   Лечится: `pending` + тяга в кадре нажатия (§3.5). Регрессия `nodip`.
3. **Двойной путь за кадр.** Кадр, в котором пауза истекла, считал и `_coast`, и
   `_thrust` на весь `dt` ⇒ шаг 2.03 клетки при норме ≤ 1.5. Лечится делением
   кадра (§3.4). Регрессия `step`.
4. **Тап недоедал клетку на 15 fps.** Явная схема интегрирования (новая скорость
   на весь кадр) обнуляла последний кадр торможения. Лечится средней скоростью
   кадра (§3.4).
5. **Мигание «до Vmax —».** `shelf_at` сбрасывался, как только скорость падала с
   полки; появился `shelf_lag` — запоминаемое время разгона серии.
6. **Отрицательная «задержка старта» после Home/End.** `go_to` не сбрасывал
   `move_at`, и лаг считался от старого нажатия. Теперь `go_to`/`press` обнуляют
   метрики серии.
7. **Ложная пауза посреди удержания.** Повтор, пришедший «реже окна», объявлялся
   новой серией; чтобы это не роняло скорость, `_coast(keep=True)` сохраняет
   попутный ход, а страховка в начале `step` возвращает газ из `покой/торможение`.
8. **`ord("щ")` в двух ветках, «тест не поймал сценарий» и т. п.** Правила,
   которые ничего не проверяют, опаснее отсутствующих: каждый такой случай теперь
   возвращает явный текст (`"сценарий не поймал паузу на ходу"`) или честный
   пропуск с `[!]` в `check`.
9. **`LC_ALL=C`** — кириллица и псевдографика исчезают молча; признак —
   `getpreferredencoding()` = «utf-8» при CODESET = ANSI_X3.4-1968 (§5).

## 10. Как дорабатывать

1. **Изменить движение** → только `Paddle` (`step`/`_run`/`_address`/`_coast`) и
   константы в шапке. Проверить: `python3 spr.py --check`,
   `python3 spr.py --trace 0.5 | head -20`, живой прогон в pty.
2. **Новый параметр** → поле в `Motion` (+ нормализация в `capped()`), флаг в
   `parse_args` с указанием значения по умолчанию, место в `draw()` («задано /
   замерено»), пример в `EPILOG` и в докстринге модуля, правило в `RULES`, если
   параметр обещает измеримое поведение.
3. **Новое правило** → функция `rule_*(motion, fps, repeat_hz, bounds, width)`,
   строка-объяснение при провале, `Rule(key, «что проверяет», fn)` в `RULES`.
   Обязательно убедиться, что правило `МИМО` на старой реализации (откат через
   monkeypatch, как в §8). Правила о подтверждении удержания обязаны пропускать
   работу вне конверта (§7.3).
4. **Менять `Rig` и `App.run` синхронно** — порядок вызовов обязан совпадать,
   иначе `--check` врёт.
5. **Не трогать** имена фаз (`PHASE_*`) без правки `draw`, правил и `--trace`
   (они сравнивают фазы строками).
6. Обновить этот файл и `README.md` (строка таблицы файлов + раздел «Стенд
   четырёх параметров»), а при изменении числа правил — счётчик в `--help`
   (`EPILOG`) и в `README.md` (сейчас 16).

## 11. Перенос чисел в `arkanoid.py`

| `spr.py` | игра | как переносится |
| --- | --- | --- |
| `--speed` (V) | `World.paddle_speed = PADDLE_TO_BALL · ball_speed` | в игре скорость выводится из размера поля; в `spr.py` она задачна — сравнивать по `V/√(ширина² + высота²)` |
| `--accel` (клеток/с²) | `paddle_accel = PADDLE_ACCEL(16/с) · paddle_speed` | переносится **отношение** `a/V` (в 1/с), а не число |
| `--brake` (клеток/с²) | `paddle_brake = PADDLE_BRAKE(21/с) · paddle_speed` | то же |
| `REVERSE_RATE` 1.5 | `PADDLE_REVERSE` 1.5 | уже одинаково |
| `--pause` | аналога в игре нет (тап = клетка сразу) | если захотите мёртвое время — это отдельное поле `World` + взведение в `tap_paddle` |
| `pending`/`confirm_window` | нет: там решение «тап/удержание» принимается до движения | если переносить мгновенный отклик, переносить и `--exact-tap`, иначе тап перестанет быть «ровно клетка» |
| `KeyRepeatTracker` (медиана, без нижнего края) | **в игре до сих пор старая версия с `REPEAT_ACCEPT[0]`** — тот же баг, что чинился здесь (§9.1) | портируется заменой `press`/`_learn`, тесты — `tests/test_physics.py::KeyRepeatTest` |
| интегрирование по средней скорости кадра | уже так (`glide_paddle_to_stop`) | — |

Алгоритм игры (сервопривод с `cmd`, `stopping_room`, `hold_paddle_command`) в
`spr.py` не воспроизводится и не должен: здесь цель — проверить четвёрку
параметров пальцем, а не сравнить две схемы управления. Для сравнения схем есть
`speed.py --variant legacy`.

## 12. Границы модели (что здесь не чинится)

* **Ритм тапа ≈ автоповтор.** Если жать клавишу строго в ритме терминала,
  различить «тап» и «держать» нечем: событие «клавишу отпустили» терминал не
  присылает. Окно подтверждения (`HOLD_TOLERANCE × gap`) — компромисс, а не
  решение; при `--exact-tap` ошибка стоит игроку задержку, при `--pause 0` —
  лишние клетки на тапе.
* **Одна клетка = один символ терминала.** При `--fps 15` шаг за кадр ≈ 4 клетки
  на Vmax = 60, и «ровно клетка» физически недостижима (вот и `--check` просит
  конверт 15…120 fps).
* **Задержка показа ≥ 1/fps.** Timestamp'ов у клавиш нет, минимальная
  дискретность — кадр цикла; «0 мс» означает «в том же кадре», не «между кадрами».
* **`--pause` короче кадра** не измерим (правила его пропускают), длиннее
  ~0.2 с — это уже не отклик, а задержка, и `rule_pause` следит, чтобы в это
  время ракета гарантированно стояла.
* Терминалы с автоповтором медленнее 200 мс (`REPEAT_GAP_LIMIT[1]`) модель
  считает тапами: порог правится в шапке файла, но вместе с ним плывёт и
  `confirm_window`.
